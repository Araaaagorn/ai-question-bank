# 01 文档总体说明（第 1 章）

> 本文档组是《AI+题库智能教学平台》的面向对象分析与设计（OOA/OOD）文档，按课程模板《面向对象分析设计文档》组织。
> 分析对象：GitHub 仓库 `Araaaagorn/ai-question-bank`（main 分支）。所有设计描述均以仓库实际代码为依据，并与需求文档交叉验证；无代码支撑的内容一律标注为**目标设计/待实现**，口径详见《04 设计依据与实现差异》。

**系统提纲挈领式说明**：本系统是面向教育场景的多教师、多学生智能题库与 AI 答疑平台（软件工程课程实践项目，monorepo）。系统由三层构成：`web/` 纯静态前端（HTML/CSS/JS，hash 路由 SPA，由后端托管）；`server/` C11 后端（libmicrohttpd 单轮询线程 + SQLite3 + libcurl + cJSON + OpenSSL，唯一公共业务入口，提供认证、题目 CRUD、AI 任务代理、教师 API 配置与日额度控制）；`ai-service/` 内部 Pi AI 服务（Node.js/TypeScript，Pi 0.84.1，仅监听 127.0.0.1，承担异步任务队列、每任务独立 Agent、三种教学技能与受限数学工具）。大模型调用由后端统一代理（DeepSeek 兼容协议），API Key 不出可信后端。用户角色为管理员（admin）、教师（teacher）、学生（student）；另有仅 platform 兼容模式使用的服务器侧运维 CLI（`scripts/ai_access.py`）。当前已实现：用户认证、题目 CRUD、AI 异步解答（solve/hint/review）、同题多轮追问、教师 API 加密配置、学生日额度（默认 20 次/学生/教师/上海自然日）；试卷管理、学生提交审核、分支讨论树 Fork、导入导出、管理后台等为目标功能（详见 04 文档状态总表）。

## 1.1 目的

本文档目的：

1. 说明软件目标——本系统旨在实现：题目资源数字化管理（题目独立实体、教师归属、知识点标签）；AI 辅助教学与答疑（后端代理大模型，完整讲解/分层提示/错因分析三种模式，异步任务机制）；师生知识协同沉淀（同题多轮追问对话）；可控的 AI 使用（教师自管 API Key 加密存储 + 学生日额度）；安全边界（Key 不出后端、会话与角色校验、路径穿越防护、敏感信息脱敏与擦除）。
2. 给出该软件的面向对象分析（OOA）模型：用况图、分析类图、顺序图、状态图、包图及完整文字描述。
3. 给出在分析模型基础上形成的面向对象设计（OOD）模型：按问题域、人机交互、控制驱动、数据管理四部分组织的设计类图、设计顺序图、设计状态图、设计包图及设计说明。
4. 记录每项设计的代码依据与实现状态（已实现/部分实现/目标设计），保证文档与项目真实情况一致。

## 1.2 应用范围

- **系统应用范围**：Web 优先部署于 Linux 课程服务器（systemd），支持多用户并发访问（Demo 阶段单实例、128 并发会话）；面向学校课程教学场景，设计上可扩展至培训机构与个人知识库场景（需求说明书 §13）。
- **面向人群**：
  | 角色 | 使用场景 |
  | --- | --- |
  | 学生（非技术） | 浏览题目、查看 AI 解答、追问讨论、（目标：个人中心/学习记录） |
  | 教师（非技术） | 题目维护、配置/启停 AI API、（目标：试卷管理、提交审核、额度策略） |
  | 管理员（技术） | 演示数据归属者、题目写权限、（目标：用户管理、审计查询、备份恢复） |
  | 运维人员（技术，非 HTTP 参与者） | 仅 platform 兼容模式经服务器 CLI 授予/撤销平台 AI 授权 |
- **本文档适用读者**：课程指导教师、项目开发与测试团队成员；作为课程阶段性检查（第二阶段：分析设计）交付物。
- **文档适用版本基线**：仓库 main 分支提交 `2420bd4`（需求与功能状态以 `docs/软件需求说明书.md`、`docs/AI题库项目整体预期功能说明书.md`、`docs/项目开发时间轴.md` §3 功能清单 F01~F19/I01~I07 为准）。

### 1.3.3 组织方式说明

1. **章节编号与模板一致**：02 文档采用模板第 2 章编号（2.1~2.5 及其子节），03 文档采用第 3 章编号（3.1~3.4 及其子节，含 3.1.6 四部分设计说明）。
2. **图形三格式并存**：每张图均有 `.puml` 源文件（可编辑、可重渲染）、`.svg`（文档引用）与 `.png`（位图备用）；渲染工具与自检脚本位于 `tools/`：`render_puml.py`（plantuml.com 官方服务优先、kroki.io 回退，批量生成 SVG+PNG）、`check_refs.py`（校验 Markdown 引用与渲染产物完整性）、`gen_msg_tables.py`（从顺序图 `.puml` **机械导出**模板要求的“对象与参与者描述”表与“对象接收发送消息的描述”表，保证图与表逐条一致）。
3. **OOA 与 OOD 的区分**：第 2 章为问题域/需求层分析模型，**独立于实现环境**（第10讲 p14）——不含 GUI 类、数据库表类、HTTP 路由与控制器；第 3 章为可实现的软件设计模型，按问题域、人机交互、控制驱动、数据管理四部分组织，并在各图文档的“设计说明”小节说明相对分析模型的新增与调整原因。两章图件不重复：OOA 的单一主动类“平台服务接口”在设计阶段被拆分为 HttpServer / RouteDispatcher / 四个控制器 / StaticFileServer（图3-1、图3-5），界面类与数据管理类均为设计阶段新增。
4. **实现状态口径**：✅ 已实现／🟡 部分实现／⬜ 目标设计（未实现）／💡 新增设计建议；所有标注的代码依据（文件/函数/表/接口）汇总于 04 文档。
5. **建议阅读顺序**：01 → 02 → 03 → 04；查图可直接按上表定位源文件。
