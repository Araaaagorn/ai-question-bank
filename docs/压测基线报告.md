## 2. 复现方法

```bash
# 1) 构建 + 启动 mock（随机延迟 300~1500ms）与 C 服务（platform 模式）
make -C server build
python3 scripts/loadtest/mock_ai_service.py --port 8001 \
    --min-delay-ms 300 --max-delay-ms 1500 &
cd server && rm -f data/bench_baseline.db
PORT=18080 DATABASE_PATH=data/bench_baseline.db WEB_ROOT=../web AQB_SKIP_ENV_FILE=1 \
  AI_ROUTING_MODE=platform AI_SERVICE_URL=http://127.0.0.1:8001 \
  AI_SERVICE_TOKEN=loadtest-token-0123456789abcdef0123456789 ./ai-question-bank-server &

# 2) 搭建环境：创建一份 active 试卷 + 授予学生平台 AI 授权
python3 scripts/loadtest/setup_env.py --url http://127.0.0.1:18080 \
    --grant-db server/data/bench_baseline.db --out tmp/loadtest/env.json
EID=$(python3 -c 'import json;print(json.load(open("tmp/loadtest/env.json"))["exam_id"])')

# 3) 逐场景压测（--duration 或 --requests 二选一）
python3 scripts/loadtest/bench.py --url http://127.0.0.1:18080 \
    --scenario health --concurrency 1 --duration 5
python3 scripts/loadtest/bench.py --url http://127.0.0.1:18080 \
    --scenario health --concurrency 16 --duration 8
python3 scripts/loadtest/bench.py --url http://127.0.0.1:18080 \
    --scenario questions --concurrency 16 --duration 8
python3 scripts/loadtest/bench.py --url http://127.0.0.1:18080 \
    --scenario login --concurrency 16 --requests 300
python3 scripts/loadtest/bench.py --url http://127.0.0.1:18080 \
    --scenario exams --concurrency 16 --duration 8
python3 scripts/loadtest/bench.py --url http://127.0.0.1:18080 \
    --scenario exam_export --concurrency 16 --duration 8 --exam-id "$EID"
python3 scripts/loadtest/bench.py --url http://127.0.0.1:18080 \
    --scenario chat_submit --concurrency 1 --requests 10 --question-id 1
```

## 4. 关键发现

### 4.1 单线程天花板：并发增加反而吞吐下降（核心动机）

`health` 无鉴权、无 DB，是纯序列化能力上限：并发 1 达 **4249 req/s**（p99 0.86ms）；并发 16 反而降至 **2921 req/s**（p99 26.9ms，~31 倍）。单线程下**并发只带来排队与调度开销、不带来吞吐**。T1-F 线程池后预期 `health c=16` 吞吐回升、延迟解耦。

### 4.2 鉴权 + DB 路径更慢，且随数据量增加

`questions`（Bearer 校验 + SQLite 读）1493 req/s，约为纯 health 的一半；`exams`（列表按角色过滤 + 逐卷读取）仅 **772 req/s**，为 questions 的一半，说明「每卷一次 DB 读取」的放大效应。改造后（T1-B 会话锁/索引 + T1-A 连接池/WAL）预期两场景提升明显。

### 4.3 试卷导出（Markdown 渲染）开销可控

`exam_export` 对**空试卷**渲染 Markdown 达 2003 req/s（快于 exams 列表）。注意当前测的是空卷（0 题）；含大量题目的导出渲染成本需在「有题目数据」的试卷上另行评估。

### 4.4 会话上限硬顶：128 个会话后登录全部失败（多用户障碍）

`login` 300 次中仅 **124 成功**、**176 次 500「创建会话失败」**。根因 `MAX_SESSIONS=128`（`auth.h:8`），每次登录新建会话、不去重，128 个活跃会话（24h）填满后 `session_create` 返回 NULL。这是「多用户同时在线」的直接障碍，需 T1-B 解决。

### 4.5 chat 慢请求把其它请求顶到秒级（单线程阻塞实证）

mock 慢响应下，`chat_submit` 每个请求阻塞 ~957ms（avg）；同窗内 `health` 的 **max 延迟被顶到 8975ms**（约为 10 个 chat 依次阻塞的排队时长），对比干净基线 0.86ms 放大约 10000 倍。这直接证实：**一个慢的内部 AI 调用就能拖垮同机所有其它请求**，是阶段三（T3-A chat 入队 + worker 池）要消除的场景，也是 T1-F 线程池后需复测的核心回归项。

## 5. 结论与后续

| 结论 | 对应改造任务 |
|------|--------------|
| 单线程并发不升反降 | T1-F（MHD 线程池）后对比 `health c=16` |
| 鉴权线性扫描 + 单连接串行 + 每卷 DB 读取放大 | T1-B（Session 索引/锁）、T1-A（连接池 + WAL） |
| 会话 128 封顶、登录 500 | T1-B（`MAX_SESSIONS` 上调 + 拷贝语义） |
| chat 慢请求把 health 顶到 ~9s | 阶段三 T3-A（chat 入队 + worker 池）、T1-F 复测 |

本报告为**改造前基线**。后续每个里程碑（M1 正确性、M2 线程池、M3 横向扩展）应复用同一脚本、同一场景重跑，与上述数字对比。
